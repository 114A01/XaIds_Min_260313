## 1. 系統是什麼

### 1.1 研究問題

專題題目是「可解釋入侵偵測系統（IDS）中，XAI 解釋的一致性能否作為信任依據」。分成兩個研究問題：

- **RQ1**：對同一筆預測，SHAP 與 LIME 兩種解釋方法的解釋一致到什麼程度？
- **RQ2**：在相同的模型信心值下，解釋一致性對「模型這次分類是否正確」有沒有額外的參考價值？

如果 RQ2 的答案是肯定的，維運人員就多了一個判斷警報可不可信的訊號。如果是否定的，結論就是「不能拿解釋一致性當信任依據」，這同樣是有效的研究結果。

### 1.2 系統的定位

XaIDS 是這個研究的**展示與資料收集工具**，不是防禦產品。它不會阻擋流量，只做偵測、解釋、記錄與統計。主實驗的統計計算（`core/run_stats.py`）和頁面用的是同一套程式，可以從 notebook 直接匯入。

### 1.3 一條 flow 的處理流程

```
來源（CSV 重播 / pcap 重播 / 網卡即時擷取）
   │  每條 flow 取出 22 個特徵
   ▼
① 預測：XGBoost 7 類 + 類別偏移 → 預測類別、信心值、ZONE
② SHAP 解釋：每個特徵對「預測類別 log-odds」的貢獻
③ LIME 解釋：同一個目標、同一個尺度、同一份背景樣本，可重複多次取平均
④ 一致性：取兩份解釋的 top-k 特徵比較（k = 3、5、7 都算）
⑤ 忠實度：把 top-k 特徵換成背景值，看預測機率掉多少
⑥ 寫入資料庫；攻擊且信心值 ≥ 60% 另外寫一筆警報
⑦ 以 SSE 即時推送到瀏覽器
```

每一條 flow 都算解釋，包含判為正常的。研究需要「判對」與「判錯」的樣本都有一致性分數，所以不設信心值門檻。

系統以「一次測試（run）」為單位管理資料。一次測試就是一次重播或一段即時擷取，有名稱、備註、來源與參數。

## 2. 安裝與啟動

### 2.1 環境

| 項目 | 目前使用的版本 |
|---|---|
| 作業系統 | Linux（WSL2） |
| Python | 3.11，conda 環境 `MLEnv` |
| 主要套件 | nfstream 6.6.0、xgboost 2.1.4、shap 0.48.0、lime、scikit-learn 1.7.2、fastapi 0.128、uvicorn 0.40、aiomysql 0.3.2 |
| 資料庫 | MariaDB 11.8，資料庫名 `xaids`，帳號密碼 `allen` / `allen`（寫在 `db/repository.py`） |
| 前端 | 伺服器端 Jinja2 樣板加原生 JavaScript，圖表用 Chart.js。Chart.js 是本地檔案，頁面不需要連外網 |

模型的訓練資料版本必須與 nfstream 版本和參數一致，升級 nfstream 前請先讀 11.4 節。

第一次在新機器上安裝：

```bash
conda create -n MLEnv python=3.11 && conda activate MLEnv
pip install -r requirements.txt
```

模型檔與測試資料不在版本控制內，要另外取得，見 11.2 節。

### 2.2 資料庫

```bash
# 確認 MariaDB 已啟動（WSL 重開機後通常要手動啟動，例如 sudo service mariadb start）
mariadb -u allen -pallen xaids -e "SHOW TABLES;"

# 新機器上還沒有資料庫與帳號時，先建立（只需要做一次）
sudo mariadb -e "CREATE DATABASE IF NOT EXISTS xaids CHARACTER SET utf8mb4;
  CREATE USER IF NOT EXISTS 'allen'@'localhost' IDENTIFIED BY 'allen';
  GRANT ALL PRIVILEGES ON xaids.* TO 'allen'@'localhost'; FLUSH PRIVILEGES;"

# 第一次使用，或要清空所有資料時才執行。這行會刪掉全部測試紀錄。
mariadb -u allen -pallen xaids < db/xaids_schema.sql
```

### 2.3 啟動伺服器

```bash
conda activate MLEnv
cd <專案根目錄>
uvicorn api.main:app --reload --port 8080
```

- **必須在專案根目錄執行**，樣板與靜態檔的路徑是相對路徑。
- 啟動時會載入模型並建立 SHAP、LIME 解釋器，需要幾秒鐘。看到 `Application startup complete.` 才算完成。
- `--reload` 會在程式檔變動時自動重啟，開發時方便。重啟會中斷正在執行的測試，正式 demo 時可以拿掉。
- 啟動時會把上次沒有正常結束、狀態還停在 running 的測試標成 stopped。

### 2.4 測試用的資料放哪裡

| 來源類型 | 目錄 | 說明 |
|---|---|---|
| CSV | 預設 `data/csv/`，可用環境變數 `XAIDS_DATA_DIR` 改目錄 | 需要含模型的 22 個特徵欄位，缺欄位的檔案會被伺服器拒絕並提示。`data/csv/` 是淨化過標籤的測試集，`label` 欄是 7 大類，細節見 6.3 節。`output/dataset/` 也是 22 特徵，但標籤**未淨化**，只在需要對照時用 |
| pcap | `data/pcap/` | 目前有 `syn-flood_1110.pcap`、`udp-flood_1110.pcap`、`sqlInjection_1110.pcap`、`BruteForce_ftp_1110.pcap`，都是自行錄製的。另有一個只有幾個封包的 `empty.pcap`，是測試「沒有 flow」的情況用的，demo 時不要選 |
| 即時擷取 | 網卡 | 見下節 |

CSV 可以有 `label` 欄。它的值可以是模型的 7 個類別，也可以是 CICIoT2023 的子類別名稱（例如 `SqlInjection`），系統會自動對應成模型類別（`Web-based`）。

### 2.5 即時擷取的權限

抓封包需要權限。目前 `MLEnv` 的 `python3.11` 已經設定了 `cap_net_raw` 與 `cap_net_admin`，一般使用者就能擷取。換機器或重建環境後要重新設定：

```bash
sudo setcap cap_net_raw,cap_net_admin=eip $(readlink -f $(which python3.11))
```

## 3. 各頁面怎麼用

所有頁面右上角可以切換亮色與暗色主題。TOP-K 的選擇（3 / 5 / 7）記在瀏覽器裡，各頁共用。

顯示測試次數、已分析的 flow 數、警報數、目前是否有測試在執行，以及模型名稱、類別、特徵清單。demo 開場時用來介紹系統。

### 3.2 測試頁 `/test`

開始一次測試的地方。

| 欄位 | 說明 |
|---|---|
| 來源 | CSV 重播、pcap 重播、即時擷取三選一 |
| 預期標籤 | 這批流量的真實類別。pcap 與即時擷取沒有逐筆標籤，填了才能算正確率。CSV 有 `label` 欄時以該欄為準 |
| 最多處理筆數 | 只處理前 N 條 flow，預設 1000，只用於 CSV 與 pcap。CSV 是從檔案開頭往下取，不是隨機抽樣。留空表示全部，但最多 200,000 條（`config.py` 的 `MAX_ROWS_LIMIT`），避免把上千萬列的檔案整個讀進記憶體 |

| 測試名稱、備註 | 名稱留空會自動命名。備註之後可以在歷史頁直接修改，名稱要進入單次測試頁修改 |

按下「開始測試」後，下方即時顯示每條 flow：ZONE、真實與預測類別、是否正確、信心值、SHAP 與 LIME 各自最重要的特徵、一致性燈號。上方計數器顯示四個 ZONE 的筆數、正確率與平均一致性。

### 3.3 展示頁 `/demo`

給觀眾看的畫面，分三塊：

## 4. 核心概念

### 4.1 信心值與 ZONE

信心值是模型對預測類別給的機率（已包含類別偏移，見 6.5 節）。ZONE 的規則：

| ZONE | 條件 | 是否產生警報 |
|---|---|---|
| `UNCERTAIN` | 信心值 < 0.6，不論類別 | 否 |
| `BENIGN` | 預測 Benign 且信心值 ≥ 0.6 | 否 |
| `SUSPICIOUS` | 預測為攻擊，0.6 ≤ 信心值 < 0.85 | 是 |
| `HIGH_CONF` | 預測為攻擊，信心值 ≥ 0.85 | 是 |

門檻在 `config.py` 的 `CONFIDENCE_LOW` 與 `CONFIDENCE_HIGH`。

### 4.2 兩種解釋

| | SHAP | LIME |
|---|---|---|
| 方法 | TreeExplainer，直接依樹的結構計算 | 在這筆資料附近產生擾動樣本，用加權線性模型近似 |
| 隨機性 | 沒有，同一筆資料結果固定 | 有，系統以固定種子讓結果可重現 |
| 解釋的目標 | 模型對「預測類別」輸出的 log-odds | 相同 |
| 參考分布 | 背景樣本：模型檔附的驗證資料抽 500 筆 | 相同的 500 筆 |
| 輸出 | 每個特徵一個有正負號的數值 | 相同 |

兩者刻意統一到同一個目標、同一個尺度（log-odds）與同一份背景樣本，才能公平比較。原因見第 8 章 Q20、Q21。

**參考分布**是解釋「相對於什麼」算出來的。SHAP 值的意思是「這個特徵讓預測比背景樣本的平均高或低多少」，LIME 的擾動樣本也是從背景樣本產生的。`config.py` 的 `SHAP_REFERENCE` 控制 SHAP 用哪一種：

| 設定 | SHAP 的參考分布 | 說明 |
|---|---|---|
| `background`（預設） | 與 LIME 相同的 500 筆背景樣本 | 兩個解釋器只差在方法 |
| `tree_path` | 樹內部記錄的訓練分布 | 2026-11-17 以前的做法，速度快約 2.5 倍，但參考分布與 LIME 不同 |

這個選擇會改變逐筆的結果。用 140 筆驗證資料（每類 20 筆）試算，兩種設定算出的 SHAP 與 LIME 平均一致性幾乎相同（k = 5 時 0.533 與 0.537），但有 54 筆的一致特徵數不同，41 筆的燈號跨過綠燈門檻。所以每次測試都會把當時的設定記在參數裡（`shap_reference`），設定不同的測試不能合併分析。

### 4.3 一致性指標

各取兩份解釋中絕對值最大的前 k 個特徵來比較：

| 指標 | 定義 | 說明 |
|---|---|---|
| `feature_agreement` | 兩邊 top-k 的交集數 ÷ k | 兩個解釋器是否挑出同一批特徵 |
| **`sign_agreement`** | 交集中正負號相同的特徵數 ÷ k | **主指標**，燈號與統計圖都用它。它一定不大於 feature_agreement |
| `rank_agreement` | 名次完全相同的特徵數 ÷ k | 最嚴格，只作輔助 |

圖表上的「一致特徵數」就是 `sign_agreement × k`，是 0 到 k 的整數。

**隨機基準**：如果兩份解釋完全是亂猜的，期望值是多少。目前 22 個特徵：

| k | feature | sign | rank |
|---|---|---|---|
| 3 | 13.6% | 6.8%（0.20 個） | 4.5% |
| 5 | 22.7% | 11.4%（0.57 個） | 4.5% |
| 7 | 31.8% | 15.9%（1.11 個） | 4.5% |

特徵只有 22 個，隨機也會有一些重疊，所以看一致性分數時一定要對照基準。

### 4.4 燈號

| 燈號 | 條件（主指標） | k = 3 | k = 5 | k = 7 |
|---|---|---|---|---|
| ● 可信 | ≥ 0.6 | 2 到 3 個 | 3 到 5 個 | 5 到 7 個 |
| ◐ 建議人工檢查 | 0.3 到 0.6 | 1 個 | 2 個 | 3 到 4 個 |
| ○ 解釋不一致 | < 0.3 | 0 個 | 0 到 1 個 | 0 到 2 個 |

門檻在 `config.py` 的 `CONSISTENCY_HIGH` 與 `CONSISTENCY_LOW`。**這是暫定值**，要等主實驗結果出來再調整。統計圖裡的「一致組」用的是同一個綠燈門檻。

### 4.5 LIME 穩定度

LIME 有隨機性。把同一條 flow 用不同種子解釋 n 次，兩兩計算 sign_agreement 再取平均，就是 LIME 穩定度。它代表「LIME 自己和自己有多一致」，是 SHAP 與 LIME 一致性的雜訊上限：如果 LIME 連自己都只有 70% 一致，就不能期待它和 SHAP 有 90% 一致。重複次數為 1 時沒有這個值。

### 4.6 忠實度（消融）

把某個解釋器挑出的 top-k 特徵換成背景資料的中位數，其餘特徵不動，重新預測，看預測類別的機率下降多少。下降越多，代表那些特徵確實是模型做出判斷的依據。SHAP 與 LIME 各算一個值，可以比較誰挑的特徵更「忠實」於模型。這個值可能是負的，表示拿掉後模型反而更有把握。

## 5. 怎麼讀統計圖

歷史頁與單次測試頁共用同一組圖。「正確」的定義是預測類別等於真實類別，只在有真實標籤的 flow 上計算。

### 5.1 摘要列

| 方塊 | 內容 |
|---|---|
| FLOWS | 納入統計的 flow 數，以及其中有真實標籤的筆數 |
| 整體正確率 | 正確 ÷ 有標籤 |
| 平均一致特徵數 | 例如 `1.84 / 5`，下方是隨機基準 |
| 錯誤率：一致 vs 不一致 | 綠燈門檻以上的那組，和以下的那組，各自的分類錯誤率與筆數 |
| AUROC | 用三種分數預測「這筆分類是否正確」的能力：只用信心值、只用一致性、兩者合併。0.5 等於亂猜，1.0 是完美 |
| LIME 穩定度 · 消融下降 | 平均穩定度，以及 SHAP / LIME 的平均消融下降量 |

### 5.2 六張圖

**圖 ① 一致性 × 筆數。** 橫軸是一致特徵數（0 到 k），縱軸是 flow 數，每根柱子堆疊「分類正確」與「分類錯誤」。回答 RQ1：一致性的分布長什麼樣子。如果錯誤的顏色集中在左邊（低一致性），就是一致性有鑑別力的初步跡象。

**圖 ② 一致性 × 分類正確率。** 同樣的橫軸，縱軸是該一致性等級的正確率，虛線是整體正確率。理想的情況是由左到右遞增。某根柱子的樣本很少時不可信，滑鼠移上去可以看到筆數。

**圖 ③ 信心值 × 筆數。** 橫軸是信心值區間，每根柱子堆疊「一致組」與「不一致組」。這張圖檢查一致性是不是只是信心值的另一種說法：如果高信心值的柱子幾乎全是一致組、低信心值的幾乎全是不一致組，兩者就高度重疊，一致性沒有新資訊。

**圖 ④ 信心值 × 分類正確率。** 這張直接對應 RQ2。每個信心值區間內有兩根柱子：一致組的正確率（綠）與不一致組的正確率（紫），灰色虛線是該區間全部 flow 的正確率。**如果在同一個區間裡，綠柱明顯高於紫柱，表示信心值相同時，一致性還能進一步分辨對錯。** 最值得看的是高信心值的區間，那裡是「模型很有把握卻判錯」的地方。

**圖 ⑤ 一致性 × 信心值。** 每個點是一條 flow，顏色是正確與否，橫向有微幅抖動避免重疊。用來直接看兩個量的關係，以及錯誤的點落在哪裡。

**圖 ⑥ 混淆矩陣。** 列是真實類別，欄是預測類別。欄固定是模型的 7 類，列只列出選取的測試裡出現過的真實類別，所以不論勾一次還是多次測試，都是同一張二維表，多選時只是列變多。格內是筆數與該列比例，對角線（判對）是藍色、其餘（判錯）是橘色，顏色深淺代表該列比例；最右欄是該類的筆數與召回率。每格底下的小字是那一格 flow 的**平均一致特徵數**：判錯的格子如果明顯低於同一列的對角線，就是一致性能指出錯誤的跡象。沒有真實標籤的 flow 不列入，筆數另外註明。用 `data/csv/` 時每個檔案只有一個真實類別，單次測試只會有一列；要看類別之間的混淆，請勾選多次不同類別的測試。

### 5.3 讀圖時的三個提醒

1. **看筆數。** 目前信心值高度集中在 0.9 以上，其他區間常常只有個位數樣本。
2. **AUROC 是樣本內的數字。** 「信心值 + 一致性」是用 logistic regression 在同一批資料上擬合再評估，會偏樂觀。正式結論要另外做交叉驗證。
3. **先確認標籤可信。** 用 `data/csv/` 的淨化資料重播，正確率才有意義。用未淨化的 `output/dataset/` 重播攻擊類 CSV 時，正確率會嚴重失真，原因見 6.3 節。

## 6. 資料與模型

### 6.1 資料集與特徵

- 資料集是 **CICIoT2023**，使用它的**原始 pcap**，不使用資料集附的 CSV 特徵。
- 用 **nfstream 6.6.0** 把封包聚合成雙向 flow。flow 以 5-tuple（來源位址、目的位址、來源埠、目的埠、協定）區分，閒置 30 秒或持續 60 秒就切出一條。
- 每條 flow 取 **22 個特徵**：協定、持續時間、封包數、位元組數、封包大小的平均 / 標準差 / 最大 / 最小、封包間隔的平均 / 最小、SYN / ACK / RST / PSH 旗標數，部分特徵再分「雙向合計」與「來源到目的」。完整清單在 `stream/flow_features.py`，每個特徵的算法在 `document/nfstream_features.md`。
- 離線萃取（訓練資料）和即時擷取用的是**同一份參數與特徵清單**。伺服器啟動時還會檢查模型檔記錄的參數與特徵是否與程式相同，不同就拒絕啟動。

不用資料集附的 CSV 有兩個原因。第一，即時擷取時無法重現資料集作者的特徵算法，線上線下會不一致。第二，我們驗證過資料集 CSV 的 `IAT` 欄位帶有標籤洩漏，見 `iat_leakage_iat_only.ipynb` 與第 8 章 Q6。

### 6.2 類別

模型分 7 類。CICIoT2023 的 20 個子類別對應如下：

| 模型類別 | 子類別 |
|---|---|
| Benign | Benign |
| BruteForce | DictionaryBruteForce |
| DoS | DoS-SYN_Flood、DoS-UDP_Flood |
| Mirai | Mirai-greeth_flood、Mirai-greip_flood、Mirai-udpplain |
| Recon | Recon-HostDiscovery、Recon-OSScan、Recon-PingSweep、Recon-PortScan、VulnerabilityScan |
| Spoofing | DNS_Spoofing、MITM-ArpSpoofing |
| Web-based | Backdoor_Malware、BrowserHijacking、CommandInjection、SqlInjection、Uploading_Attack、XSS |

這一版模型的訓練資料沒有納入 DDoS 子類別。取捨的理由記錄在 `MODEL_CARD_7class.md`，由模型作者保管，不在這個 repo 裡。

### 6.3 標籤淨化，以及為什麼原始 CSV 的正確率不能看

**這是接手的人最需要知道的一件事。**

CICIoT2023 的標籤是「擷取檔」層級的：攻擊進行期間錄到的**所有**連線都被標成該攻擊，包含同時存在的大量正常背景流量。模型訓練時做了標籤淨化，只保留真正由攻擊主機發出、符合該攻擊特徵的 flow（規則存在模型檔的 `refine_rules`，例如攻擊主機的 MAC、協定、目的埠）。

`output/dataset/*.csv` 是**未淨化**的版本，而且不含位址欄位，無法事後過濾。實際驗證的數字：

| 檔案 | 總列數 | 其中真正的攻擊 flow | 模型對攻擊 flow 的預測 | 模型對其餘 flow 的預測 |
|---|---|---|---|---|
| Mirai-udpplain | 174,250 | 3,019（1.7%） | 2,982 條判為 Mirai | 156,144 條判為 Benign |
| SqlInjection | 6,995 | 252（3.6%） | 237 條判為 Web-based | 6,615 條判為 Benign |

這張表是把模型檔的淨化規則套回 `output/flows/` 的完整 flow 資料算出來的，其中包含訓練用過的 flow，只用來說明標籤問題，不是模型的評估成績。

所以重播 `output/dataset/Mirai-udpplain.csv` 的前 150 列時，系統顯示正確率 3.3%。這 150 列裡只有 5 條是攻擊 flow，模型把其餘背景流量判成 Benign，其實是對的，卻被 CSV 的標籤算成錯誤。

**淨化過的測試集：`data/csv/`。** 為了解決這個問題，已經另外產生一份標籤乾淨的 CSV，也是伺服器預設的 CSV 目錄：

- 來源是模型的**測試切分**，套用模型檔的淨化規則後才匯出，所以不含訓練用過的 flow，正確率可以當評估數字。
- 每個子類別一個檔案（`ciciot2023_cleaned_<子類別>.csv`），每個子類別最多隨機抽 1,000 條（seed 42），共 9,787 條。
- `label` 欄已經是模型的 7 大類（例如 `ciciot2023_cleaned_XSS.csv` 的標籤是 `Web-based`），不是子類別名稱。
- 抽樣參數、子類別到大類的對照、每類淨化後可用與實際匯出的筆數，記錄在 `data/csv/summary.json`。
- 有些子類別淨化後本來就很少：Uploading_Attack 4 條、XSS 7 條、BrowserHijacking 9 條、Recon-PingSweep 11 條、CommandInjection 12 條、Backdoor_Malware 18 條。單獨跑這些檔案時，正確率與一致性的統計量只有個位數或十幾筆樣本，要合併同一大類的幾次測試再看。

結論與建議：

- **評估與 RQ2 一律用 `data/csv/`。** 不要拿 `output/dataset/` 裡攻擊 CSV 的重播正確率代表模型表現。
- `output/dataset/Benign.csv` 沒有這個問題。自行錄製、內容單純的 pcap（例如 `syn-flood_1110.pcap`）問題也小，但 pcap 沒有逐條標籤，正確率只靠「預期標籤」。

### 6.4 模型表現

模型是 XGBoost 加類別偏移。下表是模型檔內記錄的**測試集**成績，測試集使用淨化後的標籤，共 488,856 條 flow：

| 整體 | 數值 |
|---|---|
| Accuracy | 0.997 |
| Macro-F1 | 0.956 |
| Balanced accuracy | 0.949 |

| 類別 | Precision | Recall | F1 | 測試筆數 |
|---|---|---|---|---|
| Benign | 0.986 | 0.999 | 0.993 | 79,416 |
| BruteForce | 0.987 | 0.981 | 0.984 | 159 |
| DoS | 1.000 | 1.000 | 1.000 | 300,000 |
| Mirai | 0.997 | 0.987 | 0.992 | 1,535 |
| Recon | 1.000 | 0.992 | 0.996 | 106,664 |
| Spoofing | 0.953 | 0.794 | 0.866 | 998 |
| Web-based | 0.833 | 0.893 | 0.862 | 84 |

Spoofing 的召回率與 Web-based 的精確率是弱點，兩者的樣本也最少。模型檔裡另外存了一個隨機森林，測試 Macro-F1 是 0.958，與 XGBoost 相近。系統依 model card 使用 XGBoost。

### 6.5 類別偏移

資料極不平衡，直接取機率最大的類別會讓少數類別的精確率很差。模型在驗證集上學了一組每個類別的常數偏移，預測時加在 log 機率上：

```
預測類別 = argmax( log(predict_proba) + class_bias )
信心值   = softmax( log(predict_proba) + class_bias ) 中預測類別的值
```

加上偏移後，測試 Macro-F1 從 0.887 提升到 0.956。偏移是每個類別的常數，與特徵無關，所以不影響 SHAP 與 LIME 算出的特徵貢獻。實作在 `core/modelPredict.py`。

## 7. 建議的 demo 流程

### 7.1 事前檢查清單

- [ ] MariaDB 已啟動，伺服器已啟動且沒有設定 `XAIDS_DATA_DIR`（CSV 選單裡應該是 `ciciot2023_cleaned_*.csv`）。正式 demo 建議不加 `--reload`，避免中途自動重啟。
- [ ] 瀏覽器先把每一頁開過一次並強制重新整理（`Ctrl+Shift+R`）。
- [ ] 歷史頁的 RUN FILTER 只留要講的測試。**用未淨化的原始攻擊 CSV 跑出來的測試不要勾**，否則整體正確率會很難看，還得花時間解釋。
- [ ] 即時擷取先實際試過一次，確認網卡名稱、權限，以及流量產生的方式。
- [ ] 準備一個「信心值高但燈號是黃或紅」的 flow 的 Explain 連結，講解時很有說服力。

### 7.2 流程（約 8 到 10 分鐘）

1. **首頁（30 秒）**：一句話講研究問題，指出模型、7 個類別、22 個特徵。
2. **測試頁（2 分鐘）**：pcap 重播 `syn-flood_1110.pcap`，預期標籤 `DoS`，筆數 100，LIME 重複 3 次。邊跑邊說明每一欄。100 條約 50 秒；時間緊的話筆數改填 50。
3. **單筆解釋（2 分鐘）**：點一條 flow 的 Explain。說明左右是兩個解釋器對同一筆預測的說法，刻度相同，再指出 top-5 中哪幾個重疊、方向是否相同，對應到下方的一致性數字與燈號。
4. **展示頁（1 到 2 分鐘）**：說明這是維運人員會看到的畫面，每筆警報除了攻擊類型與信心值，多了一個一致性燈號。時間允許再示範即時擷取。
5. **歷史頁（3 分鐘）**：依序講圖 ①（RQ1）、圖 ④（RQ2）、摘要列的 AUROC。明確說出目前的資料量與限制。

### 7.3 即時擷取的注意事項

- 開始後至少要等 30 秒才會有第一批結果，先講別的內容，不要盯著空畫面。
- 高速攻擊（例如 SYN flood）每秒會產生極大量的 flow，系統每秒約分析 2 條，「待分析」數字會一直增加。示範時用小流量，或加 BPF 過濾。
- 按停止後，還沒分析的 flow 不會再處理。
- 備案：即時擷取出狀況時，改用 pcap 重播，展示頁同樣會即時更新。

## 8. 評審可能會問的問題

回答以目前系統的實際狀況為準。標示「尚未完成」的地方請照實說，不要硬答。

### A. 研究定位

**Q1. 這個專題的貢獻是什麼？**
把「解釋一致性」當成一個可量測的訊號，檢驗它能不能幫助判斷 IDS 警報的可信度。具體產出有三項：一套讓 SHAP 與 LIME 在同一尺度下比較的做法、一組回答 RQ1 與 RQ2 的統計方法，以及一個能在重播與即時流量上逐筆計算並展示這些指標的系統。

**Q2. 模型已經有信心值了，為什麼還需要解釋一致性？**
信心值來自模型本身，模型判錯時也常常很有把握。我們的資料裡信心值絕大多數在 0.9 以上，分辨力有限。解釋一致性來自另一個角度：兩個原理不同的解釋方法，對同一筆預測的理由是否相同。RQ2 要驗證的就是這個訊號在信心值之外有沒有額外資訊。

**Q3. 這是可以上線的 IDS 嗎？能擋攻擊嗎？**
不是，也不能。它只做偵測、解釋與記錄，定位是研究用的展示系統。沒有阻擋功能，沒有登入驗證，處理速度也不足以應付真實網路的流量。

**Q4. 目前的結論是什麼？**
主實驗還沒完成。截至 2026-11-17，資料庫裡是功能測試用的小量資料（目前模型共 6 次測試、654 條 flow）。其中一部分使用了標籤不乾淨的原始 CSV，而且都是在 SHAP 改用共同背景樣本之前跑的（見 4.2 節），不能當結論。系統與分析流程已經就緒。如果最後一致性沒有鑑別力，結論會是「不能作為信任依據」，並改以解釋的忠實度作為主要分析。

**Q5. 畫面上的一致組錯誤率比不一致組低很多，這不就是結論了嗎？**
還不能這樣說。那批資料有兩個問題：一是原始 CSV 的標籤雜訊（見 Q15），二是一致性本身會隨預測類別而不同：k = 5 時，判為 DoS 的 flow 平均一致性是 60%，判為 Benign 的只有 32%（2026-11-16 的測試，舊的 SHAP 設定；改用共同背景樣本後的驗證測試是 80% 與 46%，類別之間的差距還在）。在標籤乾淨、並且依預測類別分層分析之前，這個差異不能解讀為一致性的效果。

### B. 資料與特徵

**Q6. 為什麼不直接用 CICIoT2023 提供的 CSV 特徵？**
兩個原因。第一是一致性：即時擷取時我們沒辦法重現資料集作者的特徵算法，改用 nfstream 後，訓練與線上是同一套程式。第二是資料集 CSV 有標籤洩漏：它的 `IAT` 欄位照定義是封包時間間隔，但 95.6% 的值集中在約 8.3×10⁷，換算超過兩年，不可能是真的間隔。我們只用這一個欄位訓練深度 3 的決策樹，測試 accuracy 就有 0.979，DDoS、DoS、Mirai 的召回率都在 0.98 以上。在類別平衡的抽樣資料上，46 特徵隨機森林拿掉 IAT 後 accuracy 從 0.965 掉到 0.865。這表示用那份 CSV 訓練出的高分有一部分不是來自網路行為。完整過程在 `iat_leakage_iat_only.ipynb`。

**Q7. flow 是怎麼定義的？為什麼是 30 秒和 60 秒？**
雙向 5-tuple。閒置 30 秒視為結束，持續 60 秒強制切出。這兩個值決定 flow 怎麼切，會直接改變持續時間、封包數等特徵，所以訓練與線上必須相同，系統不開放調整。代價是偵測有 30 到 60 秒的延遲。

**Q8. 22 個特徵是怎麼選的？**
原本是 12 個基本特徵，7 類模型再加上 10 個分方向的封包大小與旗標統計。挑選過程記錄在 model card。所有特徵都是 nfstream 內建欄位，沒有自行計算的衍生值，也沒有位址與埠號，避免模型記住特定主機。

**Q9. 為什麼是 7 類？DDoS 呢？**
7 類是 CICIoT2023 的 20 個子類別歸併而成。這一版模型的訓練資料沒有納入 DDoS 子類別，理由記錄在 model card。系統本身不寫死類別數，換成 8 類模型不需要改程式。

**Q10. 標籤可靠嗎？**
原始標籤是擷取檔層級的，攻擊期間的背景流量也被標成攻擊。訓練時依攻擊主機的 MAC、協定與目的埠做了標籤淨化。例如 Mirai-udpplain 的 174,250 條 flow 中，真正的攻擊 flow 只有 3,019 條。細節見 6.3 節。

**Q11. 類別這麼不平衡，怎麼處理？**
評估時看 Macro-F1 與 balanced accuracy，不只看 accuracy。預測時加上在驗證集學到的類別偏移（見 6.5 節），Macro-F1 從 0.887 提升到 0.956。

### C. 模型

**Q12. 為什麼用 XGBoost？**
表格型的流量特徵上，樹模型的表現穩定且速度快。更重要的是 SHAP 的 TreeExplainer 可以對樹模型做精確計算，不需要近似，這讓 SHAP 這一邊的解釋沒有抽樣誤差。

**Q13. 模型的準確率是多少？**
在淨化標籤的測試集（488,856 條）上，accuracy 0.997、Macro-F1 0.956。較弱的是 Spoofing（召回率 0.794）與 Web-based（精確率 0.833）。完整表格在 6.4 節。

**Q14. 那為什麼歷史頁有些測試的正確率只有 3%，整體只有四成？**
那些測試重播的是未淨化的原始 CSV（`output/dataset/`）。之後的測試改用淨化過的 `data/csv/`，就不會有這個問題。以 Mirai-udpplain 為例，前 150 列中只有 5 條是真正的攻擊 flow，其餘是背景流量。模型把背景流量判成 Benign 是對的，但 CSV 把它們全標成 Mirai，所以被算成錯誤。這是標籤問題，不是模型問題。我們用模型檔裡的淨化規則回頭驗證過：3,019 條真正的攻擊 flow 中，模型判對 2,982 條。

**Q15. FTP 暴力破解的 pcap 幾乎全被判成 Benign，為什麼？**
這是實際觀察到的結果：97 條 flow 中 95 條被判為 Benign，平均信心值 0.89。訓練資料的 BruteForce 類只有 CICIoT2023 的字典攻擊，淨化規則只保留目的埠 22 與 554 的 flow，FTP（埠 21）不在訓練分布內。機器學習式的 IDS 對沒看過的攻擊型態泛化有限，而且會「很有把握地判錯」。這正好說明為什麼需要信心值以外的可信度訊號。

**Q16. 信心值為什麼幾乎都在 0.9 以上？有校準過嗎？**
梯度提升樹的輸出機率通常偏極端，我們沒有做機率校準。這也是信心值單獨使用時分辨力不足的原因之一。校準是可以做的後續工作。

### D. 解釋方法

**Q17. 為什麼選 SHAP 和 LIME？為什麼不用 Anchors 或反事實解釋？**
SHAP 與 LIME 是最常用的兩種事後、局部的特徵歸因方法，輸出都是「每個特徵一個有正負號的權重」，可以直接比較 top-k。Anchors 輸出的是規則，反事實解釋輸出的是「要改哪些特徵」，形式不同，無法用同一組指標比較。

**Q18. SHAP 的原理是什麼？**
把預測值拆成每個特徵的貢獻，依據是合作賽局理論的 Shapley value。所有特徵的貢獻加上基準值，剛好等於模型的輸出。TreeExplainer 利用樹的結構精確計算，同一筆資料的結果固定不變。

**Q19. LIME 的原理是什麼？**
在要解釋的這筆資料附近隨機產生許多擾動樣本，問模型這些樣本的輸出，再依樣本與原資料的距離加權，擬合一個簡單的線性模型。線性模型的係數就是解釋。它不需要知道模型內部結構，但結果會受抽樣影響。

**Q20. 兩者解釋的是同一個東西嗎？**
是，這是我們特別處理的地方。LIME 預設的分類模式解釋的是機率，SHAP 的 TreeExplainer 對多類別模型解釋的是 log-odds，而且不支援改成機率。兩個尺度不同就不能公平比較。所以我們讓 LIME 改用回歸模式，被解釋的函數設成模型對「預測類別」輸出的 log-odds，和 SHAP 完全相同。另外，兩者也用同一份背景樣本當參考分布（見 Q21）。

**Q21. 兩邊的正負號意義相同嗎？**
方向的意義相同：正值表示這個特徵目前的取值把預測推向該類別，負值表示拉離。「推向」是相對於一個基準說的，所以我們讓兩者用同一份背景樣本（驗證資料抽 500 筆）：SHAP 值是相對於這批樣本平均預測的貢獻，LIME 的擾動樣本也從這批樣本產生。如果 SHAP 不給背景資料，它的基準會是樹內部記錄的訓練分布，和 LIME 不同；我們試算過，約四成 flow 的 top-5 一致特徵數會因此改變，所以把它對齊，並把設定記錄在每次測試裡。細節上仍有差別：LIME 會先把連續特徵依四分位數切成區間，係數代表「特徵落在目前這個區間」對輸出的影響。所以我們比較的是排名與方向，不直接比較數值大小。

**Q22. LIME 有隨機性，結果可以重現嗎？**
可以。每次解釋前都重設亂數種子，同一筆資料每次執行結果相同。重複第 i 次使用「種子 + i」，重複之間彼此獨立。我們另外用 LIME 穩定度量化它的隨機性（見 4.5 節）。

**Q23. LIME 的參數怎麼設？**
每次 2,000 個擾動樣本，背景資料是模型檔附的 2,755 筆驗證資料中抽出的 500 筆，連續特徵以四分位數離散化，其餘是套件預設值。樣本數與重複次數可以在每次測試時調整，並記錄在該次測試的參數裡。

**Q24. 類別偏移會不會讓解釋和預測對不上？**
不會。偏移是每個類別的常數，不隨特徵改變，所以每個特徵的貢獻不受影響。偏移只可能改變最後選中哪個類別，而我們解釋的就是最後選中的那個類別。

### E. 一致性指標

**Q25. 為什麼主指標是 sign agreement，不是其他？**
feature agreement 只看有沒有挑到同樣的特徵，兩個解釋器即使對某個特徵的影響方向看法相反，也會算一致。rank agreement 要求名次完全相同，太嚴格，分數幾乎都很低，沒有分辨力。sign agreement 要求「挑到同樣的特徵，而且方向相同」，最接近人直覺上的「兩個解釋說法一致」。這三個指標來自 Krishna 等人討論解釋方法分歧問題的研究。三個都有計算並存入資料庫。

**Q26. k 為什麼取 3、5、7？**
人在看解釋時通常只看前幾個特徵。k 太小時指標只有少數幾個可能值，k 太大時在 22 個特徵下隨機重疊就很多。取三個值是為了確認結論不依賴某一個特定的 k。預設 5。

**Q27. 一致性 40% 算高還是低？**
要對照隨機基準。k = 5 時，兩份隨機解釋的 sign agreement 期望值是 11.4%，約 0.57 個特徵。40% 是 2 個特徵，高於隨機，但落在黃燈。

**Q28. 燈號的門檻是怎麼訂的？**
目前是暫定值：60% 以上綠燈，30% 以下紅燈。正式門檻要等主實驗結果，依信心值分層分析與 AUROC 來決定。門檻寫在設定檔，改了不需要重跑測試。

**Q29. 解釋一致，就代表模型判對了嗎？**
不代表，這正是 RQ2 要檢驗的假設。兩個解釋器可能一致地解釋了一個錯誤的預測。圖 ① 中高一致性柱子裡的「分類錯誤」部分就是這種案例。

**Q30. 兩個解釋不一致時，該相信哪一個？**
對樹模型來說，SHAP 是精確計算，LIME 是近似，忠實度指標也可以比較兩者。但系統的重點不是選一個來相信，而是把「不一致」本身當成提醒人工檢查的訊號。

**Q31. 忠實度為什麼用中位數取代，而不是直接拿掉特徵？**
樹模型的輸入欄位數是固定的，不能真的移除。換成背景資料的中位數是把該特徵設為「沒有資訊的典型值」的常見做法。

### F. 統計方法

**Q32. 怎麼判斷一致性有「額外」價值，而不只是反映信心值？**
兩個方法。第一是分層：在同一個信心值區間內，比較一致組與不一致組的正確率，也就是圖 ④。第二是 AUROC：比較「只用信心值」與「信心值加一致性」預測分類正確與否的能力，後者明顯較高才算有額外價值。

**Q33. AUROC 有沒有過度擬合的問題？**
有。頁面上「信心值 + 一致性」是在同一批資料上擬合再評估，是樣本內的數字，會偏樂觀。正式分析會在 notebook 中以交叉驗證重做，統計函式可以直接從 `core/run_stats.py` 匯入。

**Q34. 樣本數夠嗎？**
目前不夠，尤其是低信心值的區間與分類錯誤的樣本。主實驗需要更大、類別分布經過設計的測試集。系統在摘要與提示中都會顯示筆數。

### G. 系統

**Q35. 系統架構是什麼？**
nfstream 在獨立的子行程擷取封包並組成 flow，送進主行程的佇列。主行程是 FastAPI：一個專用的執行緒做預測與解釋，結果寫入 MariaDB，再用 Server-Sent Events 推送到瀏覽器。前端是伺服器端樣板加原生 JavaScript 與 Chart.js。

**Q36. 即時偵測的延遲有多久？**
主要來自 flow 的切分：一條連線要閒置 30 秒或持續 60 秒才算結束並送出分析。分析本身每條約 0.4 到 0.5 秒。所以從攻擊開始到出現警報，通常是 30 到 60 秒。

**Q37. 處理速度多快？流量很大時怎麼辦？**
本機實測約每秒 2 條 flow（LIME 2,000 樣本、重複 3 次）。時間幾乎都花在兩個解釋器上：SHAP 要對 500 筆背景樣本取期望，LIME 要產生擾動樣本。流量超過這個速度時，flow 會在佇列中排隊，展示頁的「待分析」會增加。這個設計以研究需要為優先，每一條都算完整的解釋。若要實用化，可以只對警報做解釋、降低 LIME 樣本數與背景樣本數，或平行處理。

**Q38. 警報是怎麼定義的？**
預測為攻擊類別且信心值達 60% 以上。60% 到 85% 是 SUSPICIOUS，85% 以上是 HIGH_CONF。信心值不到 60% 的歸為 UNCERTAIN，只記錄不發警報。

**Q39. 資料存在哪裡？存了什麼？**
MariaDB，五張表：測試、flow、警報、解釋、一致性。每條 flow 存 22 個特徵值、預測結果、兩個解釋器對全部特徵的權重，以及三個 k 的所有指標，所以任何分析都可以事後重做，不必重跑模型。

**Q40. 系統本身安全嗎？**
它是在本機執行的研究展示系統，沒有登入驗證，資料庫帳密寫在程式裡，不適合直接放到公開網路。

**Q41. 和 Snort、Suricata 這類 IDS 比起來如何？**
定位不同。那些是以規則為主的成熟產品。我們是機器學習式的研究原型，重點在解釋與可信度，沒有做偵測率的對照比較。

**Q42. 接下來要做什麼？**
產生標籤乾淨的測試集並完成主實驗、依結果調整燈號門檻、以交叉驗證重算 AUROC、依預測類別分層分析。之後可以考慮機率校準，以及在 SHAP、LIME 之外加入第三種解釋方法。

## 9. 已知限制

| 限制 | 影響 | 目前的處理 |
|---|---|---|
| 原始 CSV 的標籤是擷取檔層級 | 重播 `output/dataset/` 的攻擊類 CSV 時正確率嚴重失真，不能用於 RQ2 | 已產生淨化過的測試集 `data/csv/`，並設為預設 CSV 目錄，見 6.3 節 |
| 淨化後部分子類別樣本很少 | Web-based 的幾個子類別與 Recon-PingSweep 只有 4 到 18 條，單次測試的統計不穩 | 依大類合併多次測試再分析 |
| CSV 的「最多處理筆數」是取檔案前 N 列 | 檔案依時間排序，前 N 列不具代表性；留空也最多處理 200,000 列 | 需要隨機樣本時，先自行抽樣另存一份 CSV |
| 信心值集中在 0.9 以上 | 信心值分層的低、中區間樣本很少 | 區間寬度可調，解讀時注意筆數 |
| AUROC 的合併分數是樣本內擬合 | 數字偏樂觀 | 正式分析以交叉驗證重做 |
| 一致性隨預測類別不同 | 合併所有類別看時，會和類別效果混在一起 | 正式分析要依預測類別分層 |
| 燈號門檻是暫定值 | 燈號的意義尚未經過驗證 | 主實驗後調整 `config.py` |
| 即時擷取有 30 到 60 秒延遲 | 無法即時反應 | 由 flow 切分規則決定，不能調 |
| 每秒約處理 2 條 flow | 高速攻擊會大量排隊；5,000 條的測試約需 40 分鐘 | 示範時用小流量或 BPF 過濾 |
| SHAP 的參考分布是可選的設定 | 設定不同，逐筆的一致性就不同（見 4.2 節）。2026-11-17 以前的測試用的是舊設定 | 每次測試記錄設定，歷史頁預設不混用；正式結果建議兩種設定各跑一次當敏感度分析 |
| 背景樣本抽自各類筆數設有上限的驗證資料（共 2,755 筆） | 它不是實際流量的類別比例，解釋的基準因此偏向「各類平均」 | 目前的取捨，寫報告時要說明 |
| 同一時間只能跑一個測試 | 不能平行實驗 | 設計如此，LIME 解釋器不能同時解釋兩筆 |
| 測試的即時狀態存在記憶體 | 伺服器重啟會中斷測試；長時間即時擷取會持續占用記憶體 | 已分析的資料都在資料庫；長時間擷取請分段 |
| pcap 載入中無法中斷 | 大的 pcap 按停止後要等讀完 | 大檔案請設定處理筆數 |
| 模型沒看過的攻擊會被判成 Benign | 例如 FTP 暴力破解 | 模型的限制，見 Q15 |
| 沒有登入驗證 | 不能對外開放 | 僅限本機使用 |

## 10. 疑難排解

| 症狀 | 可能原因 | 處理 |
|---|---|---|
| 伺服器啟動時出現 `RuntimeError: 模型的特徵和 … 不同` | 模型檔與 `stream/flow_features.py` 的特徵或 nfstream 參數不一致 | 換回對應的模型，或依 11.4 節更新特徵清單 |
| 啟動時連不上資料庫 | MariaDB 沒有啟動，或資料庫還沒建立 | 啟動 MariaDB，必要時執行 schema |
| 頁面空白、圖沒出來、按鈕沒反應 | 瀏覽器快取了舊的 JavaScript | `Ctrl+Shift+R`。仍然不行時開瀏覽器開發者工具的 Console 看錯誤訊息 |
| CSV 開始失敗，提示缺少特徵欄位 | `XAIDS_DATA_DIR` 指到了不是 22 特徵的目錄 | 拿掉 `XAIDS_DATA_DIR` 重新啟動，回到預設的 `data/csv/` |
| 開始即時擷取時顯示網卡不存在或權限錯誤 | 網卡名稱不對，或 Python 沒有擷取權限 | 檢查網卡清單，依 2.5 節設定權限 |
| 即時擷取很久都沒有資料 | flow 尚未結束，或 BPF 把流量全濾掉了 | 等 30 秒以上，看展示頁的「已擷取」是否增加，檢查 BPF |
| 「待分析」一直增加 | 流量超過處理速度 | 停止後改用小流量或加 BPF |
| 按開始沒反應或顯示已有測試在執行 | 上一個測試還在跑 | 先按停止。狀態以 `/run/status` 為準 |
| 測試一直顯示 running 但沒有進度 | 伺服器曾經重啟 | 重新整理頁面，重啟時殘留的測試會被標成 stopped |
| 刪除按了沒反應 | 刪除是兩段式確認 | 5 秒內再按一次 |
| 透過 VS Code 連接埠轉送時請求偶爾沒有回應 | 轉送本身不穩定 | 直接用 `http://localhost:8080`。2026-11-16 前的版本在測試進行中會卡住所有請求，已修正 |
| 歷史頁統計數字和預期不同 | RUN FILTER 勾選了別的測試，或 TOP-K 不同 | 檢查勾選與 k |
| 歷史頁打開時舊的測試沒有被勾選 | 它們是其他模型或舊的 SHAP 設定跑的 | 正常。要看可以手動勾選，但不要和新的測試合併解讀 |
| 開始測試時顯示 `max_rows 需在 1 到 200000 之間` | 筆數填了 0、負數或超過上限 | 改填範圍內的數字，或留空 |
| LIME 穩定度顯示「—」 | 該次測試的 LIME 重複次數是 1 | 重複次數設 2 以上重跑 |

### 11.4 常見的修改怎麼做

**換模型**

1. 把新的模型檔放進 `saved_models/`。它必須是 joblib 的 dict，至少包含 `model`、`label_encoder`、`feature_names`、`class_names`、`validation_data`（內含 `X`）、`nfstream_params`。`class_bias` 與 `category_map` 沒有時會使用預設值。
2. 修改 `config.py` 的 `MODEL_PATH`。
3. 如果特徵變了，同步修改 `stream/flow_features.py` 的 `FEATURES`，並重新產生 CSV：`python stream/pcap_feature_extractor.py export`。
4. 重新啟動伺服器。特徵或 nfstream 參數不一致時會直接報錯，不會帶著錯誤的設定執行。
5. 舊模型的測試紀錄會保留，並標示所屬模型。歷史頁預設不會把它們混進統計。

類別數不寫死，7 類換 8 類不必改程式。唯一的假設是**正常類別的名稱必須是 `Benign`**，ZONE 的判斷用到這個字串（`core/pipeline.py` 的 `_zone`）。

**改 nfstream 參數或升級 nfstream**

這會改變 flow 的切法與特徵值。必須重跑 `extract` 與 `export`，並重新訓練模型。

**改 SHAP 的參考分布**

`config.py` 的 `SHAP_REFERENCE`，改完重啟。之後的測試會記錄新的設定，歷史頁與 `/api/stats/overall` 預設只統計與目前設定相同的測試。已經跑完的測試不會重算，要比較兩種設定就把同一份資料各跑一次。

**改門檻**

信心值與燈號門檻都在 `config.py`，改完重啟即可，不需要重跑測試，資料庫存的是原始分數。

**改 k 的清單**

`config.py` 的 `CONSISTENCY_KS`。資料庫是每條 flow、每個 k 存一列，新增的 k 只有之後的測試才有資料。

**改資料表**

修改 `db/xaids_schema.sql` 後重建會清空資料，先用 `mariadb-dump` 備份。`core/run_stats.py` 與匯出 CSV 都依賴 `consistency` 表的欄位名稱。

### 11.5 改完程式怎麼驗證

沒有單元測試。驗證靠 `tools/` 裡的兩支程式，對一個**另外啟動**的伺服器執行：

```bash
# 1. 驗證用的伺服器，不要動正在使用的 8080
uvicorn api.main:app --port 8099

# 2. API 冒煙測試：實際跑 pcap 與 CSV 各一次，檢查結果、匯出、參數檢查、重複啟動，約 1.5 分鐘
python tools/smoke_test.py --base http://localhost:8099 --keep

# 3. 前端稽核：每一頁亮、暗主題各開一次，檢查 console 錯誤、圖表、互動，並截圖
python -m venv pwenv && pwenv/bin/pip install playwright && pwenv/bin/playwright install chromium   # 只需要做一次
pwenv/bin/python tools/audit.py --base http://localhost:8099 --shots /tmp/xaids_shots --live
```

- 兩支程式都會寫進同一個資料庫。`smoke_test.py` 不加 `--keep` 時會在結束時刪除自己建立的測試；加了 `--keep` 是為了讓 `audit.py` 有資料可看，看完請到歷史頁把名稱以 `smoke` 開頭、當天建立的測試刪掉。
- `audit.py --live` 會另外啟動一次 30 筆的重播來檢查展示頁的即時更新，結束後自己刪除。
- 驗證用的伺服器啟動時，同樣會把資料庫裡狀態是 running 的測試標成 stopped，所以不要在 8080 正在跑測試時啟動它。
- 截圖要自己看過一遍，程式只能檢查「有沒有錯誤」，看不出版面跑掉。

### 11.7 容易踩到的地方

- **不要在事件迴圈上做重的計算。** 預測與解釋都在 `core/pipeline.py` 的專用執行緒裡執行。之前直接在事件迴圈上跑，測試期間所有請求都會卡住，表現出來是「按了沒反應」。
- **那個執行緒只能有一個。** LIME 解釋器內部共用亂數狀態，同時解釋兩筆會破壞可重現性。
- **改 `core/explainer.py` 時要維持三件事**：SHAP 與 LIME 解釋同一個目標（預測類別的 log-odds）、用同一份背景樣本，以及每次 LIME 解釋前重設三個亂數物件。
- **SHAP 的 `expected_value` 要在呼叫 `shap_values()` 之後才讀。** `tree_path` 設定下，呼叫前它只是 0.5 的佔位值。
- **前端不要用 `confirm()` 和 `alert()`。** 有些內嵌瀏覽器會直接擋掉，使用者只會看到按鈕沒反應。訊息一律顯示在頁面上。
- **靜態檔有版本參數**（依檔案修改時間），改了 JavaScript 不需要請使用者清快取。新增靜態檔時記得在 `base.html` 用同樣的寫法。
- **pcap 萃取與即時擷取都在以 spawn 建立的獨立行程執行。** nfstream 自己會 fork，在伺服器的執行緒裡直接呼叫會卡死。
- **`config.py` 裡的 `X_train` 其實是模型檔附的驗證資料**（2,755 筆），用作 LIME 的背景樣本與消融的中位數，不是完整的訓練集。
- **HTTP 標頭只能放 latin-1 字元。** 測試名稱可以是中文，放進標頭前要編碼，匯出 CSV 的檔名就是這樣處理的（`api/main.py` 的 `api_run_export`）。
- **過時的文件**：`xaiTechChoice.md` 是早期的選型筆記，`document/1141_presentation_slide.md` 是簡報大綱的空殼，都不代表現況。
